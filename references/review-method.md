# 审阅方法与确认记录

开始实质核对时读取。这里提供工作记录结构和判断原则，不是要求每次新增一份用户文件。

## 1. 固定文件与比较基准

记录待改 draft 和每份依据的文件名、版本／日期、角色、读取状态和定位方式。不要只按修改时间推断哪份是权威版。

对 Word 修订视图：

- 如用户已明确要求“接受全部现有修订后的正文”，在工作副本形成该视图，保留原始红线文件。
- “修改前”逐字取自该视图；历史删除文字不再混进原文，历史批注也不自动成为当前要求。
- 如果接受现有修订后已解决某问题，撤销重复、过时建议，不再为了延续上一版报告重复修改。
- 不将本轮新建议一并接受；是否采用由本轮决定记录控制。

对 Excel：用题号／题目和工作表识别项目，不把行号当题号；记录实际单元格位置。列位置改变或插入行时重新匹配，不能沿用失效坐标。

对 PDF 或图片依据：引用 PDF 阅读器页码时说明口径；印刷页码与阅读器页码不同时同时提供或明确区分。扫描件需核对关键数字、否定词和条件，不能把不确定 OCR 当原文。

## 2. 参考依据的边界

每份资料只承担使用者确认的角色：

- **唯一依据：** 本轮实质修订必须有其支持。其他资料只能用于用户允许的背景理解或提出疑问。
- **主要依据及允许补充材料：** 按用户确认的范围、优先关系和适用日期协调；不能自行用较新宣传材料覆盖指定法律文本。
- **背景资料：** 不自动构成实质改文的依据。

“不违背依据”与“得到依据支持”分别检查。参考条款未覆盖某一安排，并不能证明该安排错误；在严格模式下，该安排也不能仅靠原稿出现过就获得验证。

依据含 `[TBC]`、方括号参数、假设、例外、尚待签署或适用前提时，保留其状态。不能把草案参数抄入确定语气的正式答案。引用原文也不能证明一个机构已正式获任命、协议已签署或安排已实际投入运行。

来源内部有明显异常或冲突时，不机械照抄“唯一依据”。先列为必须解决、正确口径待确认；请求更正后的依据或明确指示。

## 3. 每项修改的最小记录

使用稳定 ID，如 R01。字段可保存于工作记录，必要时用于对话和详细版：

| 字段 | 要求 |
|---|---|
| 事项及位置 | 题号／章节／单元格；同一事项列全部关联位置。 |
| 基准原文 | 精确摘录；可含必要上下文，不能凭记忆改写后称为原文。 |
| 问题分类 | 必须解决／待确认／可选优化／可以保留。 |
| 建议修改后 | 最小替换文本；未确定的部分明确保留未决状态。 |
| 具体变化 | 哪个词、限定、主体、数字或条件变化；删除也要记录。 |
| 修改原因 | 原文问题及影响；不要只写“更专业”或“与资料一致”。 |
| 依据 | 来源标识、准确原文、条款／页码／单元格；无依据时明确缺口。 |
| 拟加 Comments | 锚点、批注文本、请谁确认什么；不臆造姓名或职责。 |
| 用户决定 | 未提交／待确认／批准修改／保留原文／暂缓，以及获准的具体范围。 |
| 交付处理 | 正文采用内容、占位处理、是否仍影响对外使用。 |

一个事项包含多处替换时，确认覆盖哪些位置要明确。用户仅批准其中一处，不代表其他具有不同实质影响的位置也被批准。

将相同事实缺口合并成一个具体问题，让同事一次回答；避免为每道相关题重复提出同样确认。

## 4. 检查逻辑与最小修改

逐项问：

1. 原稿是否回答问题本身及其子问题？是否把 Guidance 当事实？
2. 责任主体、法律身份、权利与操作机制是否混淆？
3. 数值的单位、币种、分母、适用场景及日期是否一致？
4. 限定条件、例外和承诺强度是否完整？
5. 同一事实在其他题目、语言版本或章节是否矛盾？
6. 最少改哪几个词或哪一项限定就能解决问题？

按以下通用边界判断，不从其他任务移用事实或结论：

- **直接冲突：** 对同一主体、事项和适用范围，原稿与指定依据表达相反结论时，提出最小修正，完整保留依据中的条件与例外，等待批准。
- **证据缺口：** 依据未提及某项事实，不证明该事实不存在；也不支持新增、删除或替换该事实。列出需确认内容及缺少的依据。
- **角色与权限：** 职责、身份、授权与实际操作分别核对。对某项工作的参与或支持，不自动证明承担另一项职责，也不证明拥有更广权限。
- **机制与实施细节：** 依据确认采用某种机制，不等于确认其所有参数、参与者、操作步骤或实施状态。仅写入得到明确支持且获准采用的内容。
- **限制与许可：** 对某项活动的限制、资格或前提，不自动构成另一项活动的许可；不同控制措施或业务安排也不互相替代。
- **范围与条件：** 判断差异前先核对对象、场景、适用期间、条件及例外。适用范围不同的表述不直接判为矛盾。
- **参数不确定性：** 数字或单位不一致时必须解决差异；参考稿中的占位值、方括号参数或待确认值不自动优先，也不转写为确定事实。
- **语义强度：** 改变可能性、义务、否定、权限范围或承诺强度，均按实质修改处理。含糊的连接词或符号不能自行解释成累计要求、先后顺序或可选关系。

“语法优化”也可能改变否定关系、并列关系和条件范围。无法证明等义时，作为实质改动提出。

## 5. 两道确认怎样衔接

第一道确认锁定本轮任务、基准、依据和输出。第二道确认针对读完资料后发现的具体问题、替换文本、拟加批注和未决处理。

- 已确认事项直接沿用，不把每次工具操作变成新的审批。
- “可以，按这份清单做”足以批准其明确列示的范围；“方向可以”不自动批准尚未展示的新增实质内容。
- 用户追加明确指示时，将其并入记录；只有指示与既有约束冲突、或缺少执行所必需信息时再问。
- 用户确认保留一项未经依据支持的内容时，记录其确认性质。使用者的业务确认不自动变成律师确认，需明确是否改变唯一依据的边界。
- 用户要求暂缓部分内容时，已确认的其他部分可以继续；交付必须如实标明暂缓／未决范围。

## 6. 中英文分别核对

确认哪种语言是权威正文。辅助中文应忠实表达原文及修改后的意思，不借翻译扩写或修正英文。

两种语言均为正式稿时，分别定位原文，展示各自修改；一版批准不能掩盖另一版新增的含义。不得默认中英文严格一一对应；先报告原有差异，再提统一方案。

重点比对责任主体、权利、否定、日期、数字、货币、条件、例外及 may／shall／will 等语气。文献原文为英文时，详细版的中文翻译注明为译文，不能伪装成参考文件原文。
